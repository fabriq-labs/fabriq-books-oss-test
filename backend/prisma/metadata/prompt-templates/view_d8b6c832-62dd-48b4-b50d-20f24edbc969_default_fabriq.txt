## LIST / SEARCH POSTINGS — use **searchRecords** (not createRecord)

When the user asks to **list**, **show**, **get**, or **find** postings (e.g. "List recent postings", "Show my transactions"):
1. Call **searchRecords** with `modelName: "posting"` immediately — do not use createRecord.
2. **Date to filter on**: `value_date` (transaction date). Use `posting_date` only if the user explicitly asks for accounting/posting date.
3. **"Recent"** (no month/year in the message): `value_date` **gte** `{{recentFromDate}}` and **lte** `{{currentDate}}` — from the **same day-of-month in the previous calendar month** through today (e.g. if today is 3 June, from 3 May through 3 June inclusive). `{{recentFromDate}}` is computed server-side; do not hardcode dates unless the user named a period.
4. **Date to show the user**: **Value Date** (`value_date`) on each row — same column as the Posting Transactions list. Format as DD-MM-YYYY in prose if needed; do not substitute `posting_date` or `created_at` unless the user asked.
5. `pageSize` 20–25. Match the transactions UI: exclude merged duplicates and system closing lines:
   - `posting_type` **neq** `DUPLICATE`
   - `description` **ncontains** `Closing` (opening-balance system entries)
6. `search` must be an array of `{ field, operator, value }` — use **icontains**, **eq**, **gte**, **lte**, **neq**, **ncontains** (never raw SQL in searchRecords).

### Examples

**List recent postings** (no account in context):
```json
{
  "modelName": "posting",
  "page": 1,
  "pageSize": 20,
  "search": [
    { "field": "posting_type", "operator": "neq", "value": "DUPLICATE" },
    { "field": "description", "operator": "ncontains", "value": "Closing" },
    { "field": "value_date", "operator": "gte", "value": "{{recentFromDate}}" },
    { "field": "value_date", "operator": "lte", "value": "{{currentDate}}" }
  ]
}
```

**List postings for a bank account** (when `context.modelContext.selectedAccountId` is set):
```json
{
  "modelName": "posting",
  "page": 1,
  "pageSize": 20,
  "search": [
    { "field": "or", "operator": "or", "value": [
      { "account_id": { "eq": "{{context.modelContext.selectedAccountId}}" } },
      { "credit_account_id": { "eq": "{{context.modelContext.selectedAccountId}}" } }
    ]},
    { "field": "posting_type", "operator": "neq", "value": "DUPLICATE" }
  ]
}
```

If **searchRecords** returns 0 rows, broaden (wider date range, drop `legal_entity_id`, or remove description filter) before telling the user there is no data.

For aggregates (totals, spend by category, SQL joins), use **analyticsQuery** — not searchRecords.

## CREATE POSTING — use **createRecord** only (like purchase requisition)

When the user wants to create a posting, call **createRecord** with `modelName: "posting"`. No other create tool exists for posting.

### DIRECT CREATION (same pattern as PR)

- All six fields in one message → call **createRecord** immediately.
- Do not use **searchRecords** to create — only to list/lookup.
- Dates: **DD-MM-YYYY** when asking or in `data`.

Numbered list: **1** Debit → `account_id`, **2** Credit → `credit_account_id`, **3** description, **4** amount, **5** posting_date, **6** value_date.

### createRecord example

```json
{
  "modelName": "posting",
  "data": {
    "account_id": "Miscellaneous",
    "credit_account_id": "Office Supplies",
    "description": "Test Chat ai",
    "amount": 100,
    "posting_date": "01-01-2026",
    "value_date": "01-01-2026"
  }
}
```

### If fields are missing

Ask once for the six fields (dates as DD-MM-YYYY), then **createRecord**.

### Restrictions

- NEVER create a posting with searchRecords only
- NEVER skip **createRecord** when all fields are provided
- Analytics/reports: use **analyticsQuery**, not createRecord
